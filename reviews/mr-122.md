# MR !122 — Import-resolution floor

## Finding 1 — High — Repositories with only external imports are falsely labeled as resolver failures

`src/metrics/coupling/mod.rs` computes `resolved edges / extracted specifiers` and treats a rate at or below 2% as proof that the language resolver cannot see the layout. A valid small application that imports React and no local module has one extracted specifier, zero internal edges, and is therefore reported as a broken/unmeasured resolver. The same happens in a correctly resolved repository whose dependencies are intentionally all external.

The counter cannot distinguish “resolver failed” from “there were no repository-local targets to resolve.” Gate this diagnostic on independently identifiable local candidates, a language/layout capability probe, or report the state as ambiguous rather than asserting resolver failure and suppressing otherwise valid zero-coupling results.

## Finding 2 — Medium — A global rate lets one language suppress valid data from another

The resolution rate is snapshot-wide. In a mixed-language repository, a large C# area with many unresolved `using` directives can push the rate below 2% even when a smaller Rust/TypeScript area has a valid, non-empty import graph. All three import metrics then become unscored, discarding the valid edges that were collected.

Track extracted/resolved counts per language (or per resolver) and either exclude only failed languages from the graph metrics or clearly expose partial coverage.
